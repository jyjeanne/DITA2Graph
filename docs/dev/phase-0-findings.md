# Phase 0 spike findings

Status of the Phase 0 exit criteria from `docs/plugin-specification.md`
§12, and what they changed about the plan in §3.

## What was checked

1. **Are `okf-rs` crates usable as Rust library dependencies (not just
   CLI-only)?** Yes. `okf-core`, `okf-parser`, `okf-dita`, `okf-generator`,
   and `okf-validator` all compile cleanly as git dependencies
   (`{ git = "https://github.com/jyjeanne/okf-rs" }`, currently at crate
   version `0.3.0`, no `crates.io` publish yet — pin the git rev, not a
   branch, once this moves past spiking). Confirms the first half of the
   §3/§12 Phase 0 assumption.

2. **Does the reuse plan in the original §3 draft hold up once you read
   the actual source?** Partially — two corrections came out of this:

   - **`okf-dita::import_dita` is not a DITA-OT-aware extractor.** It
     walks `.dita`/`.xml` files with a dependency-free `roxmltree` parser
     and turns *each file* into one generic `Document` concept. It does
     not resolve `keyref`/`conkeyref`, does not know about `topicref`
     hierarchy or DITAVAL filtering, and cannot distinguish a `task` from
     a `concept` topic. It's useful as a fallback/reference implementation
     for teams without DITA-OT, and its `export_dita` direction may be
     useful later for round-tripping, but it is **not** the DITA→OKF
     extraction path DITA2Graph needs (that's still DITA-OT's own
     resolved preprocessing output, §2.2, feeding the normalized model,
     §3.2). The original spec text overstated this ("the natural starting
     point for the DITA→OKF direction") and undersold how much of §3.2's
     job is genuinely DITA2Graph-specific.

   - **`okf-generator`/`okf_parser::Concept` are hardcoded to a
     source-code vocabulary.** `ConceptKind` is `Package | Module | Class
     | Trait | Interface | Struct | Enum | Function | Method | Variable |
     Constant | Document` — no `Task`/`Reference`/`Concept`/`Glossary
     Entry`. `RelationKind` is `Imports | Calls | CalledBy | Implements |
     Inherits | DependsOn | MemberOf` — no `requires`/`applies-to`/
     `contains`/`generated-from` (§4.3). `okf-generator::write_bundle`
     writes exactly that model's `type`/`relationships` shape. There is no
     way to get DITA2Graph's OKF mapping (§4.1) out of it without either
     upstream changes to `okf-rs` or writing a separate bundle writer.

   **Decision:** `dita2graph-core` writes its OKF bundle directly (a small
   dedicated writer, `core/dita2graph-core/src/okf.rs`) rather than
   depending on `okf-generator`. The OKF v0.2 *format* is just markdown +
   YAML frontmatter with `type` as the only required key — nothing about
   conformance requires going through `okf-rs`'s typed Rust API, and this
   is confirmed empirically (see below): the directly-written bundle
   round-trips cleanly through `okf_validator::validate_bundle`.

3. **Is `okf-validator` still reusable given the above?** Yes, and this
   is the one part of the original reuse table that holds exactly as
   planned. `okf_validator::validate_bundle(bundle_dir: &Path) ->
   Result<ValidationReport>` walks the bundle on disk and validates raw
   parsed frontmatter (required `index.md`, frontmatter shape, dangling
   markdown links, reachability from `index.md`, duplicate ids) — it does
   not require the typed `Concept` model, so it works unmodified against
   a hand-written or independently-generated bundle, "generated by
   `okf-generator` or hand-edited" per its own module docs. Confirmed
   empirically: `dita2graph-core`'s bundle passes it (see below).

   **Gap found:** `okf-validator` v0.3.0 checks relationship-target
   resolution only for its own known keys (`calls`/`called_by`/`imports`/
   `member_of`/...) — it has no knowledge of DITA2Graph's `relations`
   frontmatter extension (`requires`/`applies-to`/`contains`), so a
   dangling `relations` target would not be caught by it. The plain
   markdown links every relation also gets (§4.1) *are* checked (the
   generic "markdown links resolve" rule), which is why the extension
   field was designed as additive in the first place — but a
   DITA2Graph-specific validator rule for `relations` link-integrity
   is still a real gap, tracked as follow-up work (§10).

   **Second gap found:** `okf-validator` does not implement the OKF
   spec's `log.md` reserved-filename exemption (`§3.1` of the OKF spec:
   "the following filenames have defined meaning ... and MUST NOT be
   used for concept documents: `index.md`, `log.md`") the way it does for
   `index.md` (`is_index`). A `log.md` written without concept-shaped
   frontmatter is flagged as an invalid, orphaned concept. `dita2graph-core`
   does not write `log.md` yet as a result — see the comment in `okf.rs`
   — rather than ship a bundle that fails its own validation gate. Revisit
   once upstream handles it, or add a local carve-out to the validation
   step if it doesn't.

4. **Does DITA-OT's resolved preprocessing output actually expose
   everything §2.2/§3.2 assume (resolved `keyref`/`conref`, DITAVAL
   filtering, `topicref` hierarchy)?** **Not yet checked.** This requires
   an actual DITA-OT 4.4 install and a live `dita --format <transtype>`
   run, which wasn't attempted in this session (no `dita` binary
   available; a full DITA-OT release is a large download). This remains
   the single biggest open Phase 0/1 risk and the top of the next
   session's list — see "Next steps" below.

## What got built off these findings

- `core/dita2graph-core`: the normalized-model types (§3.2), the OKF
  bundle writer (§4), a `DITA2GRAPHnnnX` diagnostics module (§2.5), and a
  `build`/`validate`/`query` CLI (§3.4). All real, compiled, and covered
  by passing tests (`cargo test -p dita2graph-core`), including a test
  that builds a bundle from the same fixture used in `sample-docs/` and
  round-trips it through `okf_validator::validate_bundle` with zero
  errors.
- `mcp/dita2graph-mcp`: the JSON-RPC-over-stdio server (§5.5) with the
  DITA-specific tool set (§5.2) — `search_topics`, `find_related_topics`,
  `explain_task`, `trace_dependencies`, `generate_summary`,
  `validate_bundle` — reading the bundle `dita2graph-core` writes.
  Exercised manually end-to-end over stdin/stdout against the
  `sample-docs/` fixture (see the repo README for the transcript) and
  covered by protocol/tool tests.
- `sample-docs/`: a small fixture DITA project (one map, one task, one
  concept, one plain topic; `install-task`/`config-concept` keys;
  `audience="admin"`/`product="enterprise"` profiling) matching the
  examples already in spec §3.2/§4.4, plus a `normalized-model.sample.json`
  standing in for what DITA-OT extraction will eventually produce
  automatically — hand-authored, not machine-generated, since the Java
  extraction side doesn't exist yet (finding 4).
- `plugin/org.dita.dita2graph`: `plugin.xml`/`build.xml`/`cfg/*.xml`/
  `bin/dita2graph` skeleton per §2.1, explicitly flagged in-file as
  unverified against a live DITA-OT install.

## Corrections made to the spec

`docs/plugin-specification.md` §3's reuse table and surrounding text
should be read alongside this document; a follow-up edit will fold
findings 2–3 back into §3 directly (marking `okf-dita`/`okf-generator` as
not reused for the core write path, and adding the two `okf-validator`
gaps above) rather than leaving the correction only here.

   `plugin/org.dita.dita2graph`; confirm it installs without error.

   hand-written JSON fixture.
