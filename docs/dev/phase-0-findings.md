# Phase 0 spike findings

Status of the Phase 0 exit criteria from `docs/plugin-specification.md`
§12, and what they changed about the plan in §3.

## What was checked

1. **Are `okf-rs` crates usable as Rust library dependencies (not just
   CLI-only)?** Yes. `okf-core`, `okf-parser`, `okf-dita`, `okf-generator`,
   and `okf-validator` all compile cleanly as git dependencies
   (`{ git = "https://github.com/jyjeanne/okf-rs" }`, currently at crate
   version `0.3.0`, no `crates.io` publish yet — pin the git rev, not a
   branch, once this moves past spiking). Confirms the first half of the
   §3/§12 Phase 0 assumption.

2. **Does the reuse plan in the original §3 draft hold up once you read
   the actual source?** Partially — two corrections came out of this:

   - **`okf-dita::import_dita` is not a DITA-OT-aware extractor.** It
     walks `.dita`/`.xml` files with a dependency-free `roxmltree` parser
     and turns *each file* into one generic `Document` concept. It does
     not resolve `keyref`/`conkeyref`, does not know about `topicref`
     hierarchy or DITAVAL filtering, and cannot distinguish a `task` from
     a `concept` topic. It's useful as a fallback/reference implementation
     for teams without DITA-OT, and its `export_dita` direction may be
     useful later for round-tripping, but it is **not** the DITA→OKF
     extraction path DITA2Graph needs (that's still DITA-OT's own
     resolved preprocessing output, §2.2, feeding the normalized model,
     §3.2). The original spec text overstated this ("the natural starting
     point for the DITA→OKF direction") and undersold how much of §3.2's
     job is genuinely DITA2Graph-specific.

   - **`okf-generator`/`okf_parser::Concept` are hardcoded to a
     source-code vocabulary.** `ConceptKind` is `Package | Module | Class
     | Trait | Interface | Struct | Enum | Function | Method | Variable |
     Constant | Document` — no `Task`/`Reference`/`Concept`/`Glossary
     Entry`. `RelationKind` is `Imports | Calls | CalledBy | Implements |
     Inherits | DependsOn | MemberOf` — no `requires`/`applies-to`/
     `contains`/`generated-from` (§4.3). `okf-generator::write_bundle`
     writes exactly that model's `type`/`relationships` shape. There is no
     way to get DITA2Graph's OKF mapping (§4.1) out of it without either
     upstream changes to `okf-rs` or writing a separate bundle writer.

   **Decision:** `dita2graph-core` writes its OKF bundle directly (a small
   dedicated writer, `core/dita2graph-core/src/okf.rs`) rather than
   depending on `okf-generator`. The OKF v0.2 *format* is just markdown +
   YAML frontmatter with `type` as the only required key — nothing about
   conformance requires going through `okf-rs`'s typed Rust API, and this
   is confirmed empirically (see below): the directly-written bundle
   round-trips cleanly through `okf_validator::validate_bundle`.

3. **Is `okf-validator` still reusable given the above?** Yes, and this
   is the one part of the original reuse table that holds exactly as
   planned. `okf_validator::validate_bundle(bundle_dir: &Path) ->
   Result<ValidationReport>` walks the bundle on disk and validates raw
   parsed frontmatter (required `index.md`, frontmatter shape, dangling
   markdown links, reachability from `index.md`, duplicate ids) — it does
   not require the typed `Concept` model, so it works unmodified against
   a hand-written or independently-generated bundle, "generated by
   `okf-generator` or hand-edited" per its own module docs. Confirmed
   empirically: `dita2graph-core`'s bundle passes it (see below).

   **Gap found:** `okf-validator` v0.3.0 checks relationship-target
   resolution only for its own known keys (`calls`/`called_by`/`imports`/
   `member_of`/...) — it has no knowledge of DITA2Graph's `relations`
   frontmatter extension (`requires`/`applies-to`/`contains`), so a
   dangling `relations` target would not be caught by it. The plain
   markdown links every relation also gets (§4.1) *are* checked (the
   generic "markdown links resolve" rule), which is why the extension
   field was designed as additive in the first place — but a
   DITA2Graph-specific validator rule for `relations` link-integrity
   is still a real gap, tracked as follow-up work (§10).

   **Second gap found:** `okf-validator` does not implement the OKF
   spec's `log.md` reserved-filename exemption (`§3.1` of the OKF spec:
   "the following filenames have defined meaning ... and MUST NOT be
   used for concept documents: `index.md`, `log.md`") the way it does for
   `index.md` (`is_index`). A `log.md` written without concept-shaped
   frontmatter is flagged as an invalid, orphaned concept. `dita2graph-core`
   does not write `log.md` yet as a result — see the comment in `okf.rs`
   — rather than ship a bundle that fails its own validation gate. Revisit
   once upstream handles it, or add a local carve-out to the validation
   step if it doesn't.

4. **Does DITA-OT's resolved preprocessing output actually expose
   everything §2.2/§3.2 assume (resolved `keyref`/`conref`, DITAVAL
   filtering, `topicref` hierarchy)?** **Yes, confirmed.** DITA-OT 4.4 was
   downloaded and run for real (`gradle-build/`, finding 5) against
   `sample-docs/`. Its `html5` transtype builds `sample-docs/` cleanly
   end to end, and the resolved intermediate topic file for
   `installing-product.dita` shows exactly what §3.2 assumes: the
   `<xref keyref="config-concept">` resolved to a concrete
   `href="configuration.dita"`, and `audience="admin"
   product="enterprise"` preserved on the root element. This closes what
   was the single biggest open Phase 0/1 risk.

5. **Does the spec's §8.2 Kotlin DSL `build.gradle.kts` example actually
   compile and run, and does the plugin's `plugin.xml`/`build.xml`
   skeleton (§2.1) actually install and dispatch correctly against a
   live DITA-OT 4.4?** Checked directly, in `gradle-build/` (a real
   Gradle 9.6.1 project, wrapper-pinned, run against JDK 21 — JDK 25
   wasn't available in this sandbox and Gradle's toolchain
   auto-provisioning couldn't reach `api.foojay.io` to fetch one; DITA-OT
   4.4 only requires 17+, so this doesn't affect the findings below, only
   means JDK 25-specific behavior is itself unverified). This surfaced
   five real bugs, none of them guesses — each confirmed by reading
   `dita-ot-gradle`'s actual Kotlin source or DITA-OT's own bundled
   plugins, not assumed:

   **a. §8.2's Kotlin DSL property calls didn't match the real API.**
   `plugins(listOf(...))` doesn't compile — `DitaOtInstallPluginTask
   .plugins` is `fun plugins(vararg pluginIds: String)`, not a function
   taking a `List`. `force(true)` doesn't compile at all — `force` is a
   bare `Property<Boolean>` with no Groovy-DSL-friendly wrapper function,
   so it needs `force.set(true)`. `DitaOtValidateTask` uses `ditaOtDir(dir:
   Any)`, not `ditaOt(...)` (that name only exists on `DitaOtTask`).
   `DitaLinkCheckTask` has no `ditaOtDir` property at all — it's a pure
   Kotlin XML link scanner with no DITA-OT dependency, confirmed from its
   source, so it shouldn't `dependsOn(downloadDitaOt)` or take a
   `ditaOtDir` either. Fixed in both `gradle-build/build.gradle.kts` and
   spec §8.2 (§8.2 also picked up a `tasks.register<Type>("name") { }`
   rewrite, since the original `by tasks.registering(Type::class)` form
   is deprecated as of Gradle 9.6 and warns it's incompatible with
   Gradle 10).

   **b. XML comments containing `--` are illegal and DITA-OT's parser
   enforces it.** Multiple files (`plugin.xml`, `build.xml`,
   `cfg/dita2graph.xml`, `sample-docs/public.ditaval`) had comments using
   `--` as an em-dash or quoting a `--flag` literally — legal in most
   contexts but a hard XML parse error (`[Fatal Error] plugin.xml:3:25:
   The string "--" is not permitted within comments.`), which is exactly
   how `dita install` failed the first time it was tried. Fixed
   everywhere (verified with a script that checks every `<!-- ... -->`
   body for `--`, not just eyeballing it — the fix itself introduced a
   second violation the first time around).

   **c. `dita.transtype` and `dita.conductor.transtype.check` are not
   real DITA-OT extension points.** Confirmed by grepping every bundled
   plugin's `plugin.xml` in the downloaded DITA-OT 4.4 for
   `<extension-point>` declarations: neither exists. `org.dita.base`
   declares `ant.import` and `dita.conductor.target.relative` instead,
   and `org.dita.html5`/`org.lwdita` both register their transtype with a
   top-level `<transtype name="..." desc="..."/>` element and wire their
   Ant build file in via `<feature extension="ant.import" file="..."/>`.
   `plugin.xml` rewritten to match; this was the cause of "Integration
   failed: ... uses an undefined extension point dita.transtype".

   **d. `dita.conductor.lib.import` takes no `type` attribute.** No real
   plugin.xml among DITA-OT 4.4's bundled plugins passes one. Removed
   (harmless either way, but wrong).

   **e. DITA-OT's transtype-to-Ant-target dispatch has two undocumented
   (in this spec) requirements**, both found by trial and error against
   the real toolkit, not by reading a spec DITA-OT itself doesn't publish
   here:
   - The Ant target's name must be `dita2` + the transtype value, *not*
     the transtype value alone. `org.dita.html5`'s `transtype
     name="html5"` dispatches to a target literally named `dita2html5`.
     Our transtype is already named `dita2graph`, so the real working
     target name is the admittedly-odd `dita2dita2graph` — confirmed by
     `Target "dita2dita2graph" does not exist in the project "null"`
     once the target-naming fix above was in place.
   - The target must `depends="build-init,preprocess2"`, not just
     `depends="preprocess"`. `build-init`'s `init-properties` sub-target
     is what actually defines `${dita.temp.dir}` and the Ant project
     references (`Store`, `XML utils`) DITA-OT 4.4's map-first
     (`preprocess2`) pipeline needs; skipping it produced `${dita.temp
     .dir}` appearing *unsubstituted* in a log line and then a bare
     `NullPointerException` deep inside `build_preprocess2.xml`, with no
     other diagnostic. `org.dita.html5`'s real target depends on
     `html5.init,build-init,preprocess2,...` — `build-init` is the part
     that was missing here, adapted rather than the whole html5-specific
     chain since our target doesn't need html5's own init step.

   **Result after all five fixes:** `dita --format dita2graph --input
   sample-docs/user-guide.ditamap` runs DITA-OT 4.4's real preprocessing
   pipeline against `sample-docs/` and reaches our target successfully
   (`BUILD SUCCESSFUL`, confirmed with a temporary `<echo>` in place of
   the real extraction task). The *only* remaining failure, restored to
   `build.xml` for the final state, is exactly the one already predicted:
   `dita2graph:extract` is unbound because `lib/dita2graph-core.jar`
   doesn't exist yet (§2.1, Phase 1 backlog item 3, unchanged). Verified
   both via the raw `dita` CLI and via the real Gradle task graph
   (`./gradlew validateDocs checkLinks` — real pass; `./gradlew
   installDita2Graph` / `buildKnowledgeGraph` — fail exactly at "Library
   file not found: .../lib/dita2graph-core.jar", the correct and expected
   failure).

6. **Once `ExtractTask` and a real `lib/dita2graph-core.jar` existed
   (written in this session, see below), did wiring them into `build.xml`
   actually work first try?** No — two more real bugs, again confirmed
   by trial and by reading DITA-OT's own build files, not guessed:

   - **`${args.dita2graph.*}` properties were never actually set to
     anything.** `build.xml` referenced e.g. `${args.dita2graph.store}`
     assuming a default would materialize from somewhere, but nothing
     did — `cfg/dita2graph.xml`'s `<dita2graph-config>` format is a
     DITA2Graph invention DITA-OT never reads, and no `<transtype><param>`-
     style default was ever wired up either. Without an explicit CLI
     `--args.dita2graph.store=...`, the property stayed the literal,
     unresolved string `"${args.dita2graph.store}"`. Fixed with plain
     Ant `<property name="args.dita2graph.store" value="sqlite"/>`
     defaults at the top of the target — Ant's `<property>` never
     overrides an already-set value, so a real CLI override still wins,
     and this needs no DITA-OT-specific mechanism to reason about.
   - **`outputDir="${output.dir}"` was the wrong property.** `output.dir`
     is only `build-init`'s own fallback default (`${dita.dir}/out`);
     the property actually populated from the CLI's `--output` argument
     is `dita.output.dir`, confirmed by grepping `org.dita.html5`'s real
     build file for how it wires its own output directory. Using
     `output.dir` would have silently written the bundle to the wrong
     place instead of failing loudly.

   Both fixed directly in `build.xml`.

7. **Does `dita-ot-gradle`'s `DitaOtInstallPluginTask` install a plugin
   straight from its source directory, the way `gradle-build/`
   originally passed it?** No. Its "local" install path needs a ZIP
   file — "absolute path" in its own docs means a path *to a `.zip`*,
   not a plugin directory — confirmed the same way the very first XML-
   comment bug was: `dita install <directory>` fails with "Failed to
   expand .../org.dita.dita2graph to .../plugin", the same error
   `java.util.zip` gives trying to read a directory as a zip stream.
   Fixed by adding a `Zip` task (`zipDita2GraphPlugin`) to
   `gradle-build/build.gradle.kts` ahead of `installDita2Graph`, and
   pointing `plugins(...)` at the zip's output file instead of the raw
   plugin directory.

   **Result:** `./gradlew buildKnowledgeGraph` in `gradle-build/` now
   runs the entire pipeline for real — download DITA-OT, zip and install
   the plugin, validate, check links, and run the `dita2graph` transtype
   — and produces a real, `okf_validator`-passing OKF bundle at
   `gradle-build/build/dita2graph/okf/`. So does the raw `dita` CLI
   directly. Both confirmed by inspecting the actual generated bundle
   files, not just a zero exit code.

## What got built off these findings

- `core/dita2graph-core`: the normalized-model types (§3.2), the OKF
  bundle writer (§4), a `DITA2GRAPHnnnX` diagnostics module (§2.5), and a
  `build`/`validate`/`query` CLI (§3.4). All real, compiled, and covered
  by passing tests (`cargo test -p dita2graph-core`), including a test
  that builds a bundle from the same fixture used in `sample-docs/` and
  round-trips it through `okf_validator::validate_bundle` with zero
  errors.
- `mcp/dita2graph-mcp`: the JSON-RPC-over-stdio server (§5.5) with the
  DITA-specific tool set (§5.2) — `search_topics`, `find_related_topics`,
  `explain_task`, `trace_dependencies`, `generate_summary`,
  `validate_bundle` — reading the bundle `dita2graph-core` writes.
  Exercised manually end-to-end over stdin/stdout against the
  `sample-docs/` fixture (see the repo README for the transcript) and
  covered by protocol/tool tests.
- `sample-docs/`: a small fixture DITA project (one map, one task, one
  concept, one plain topic; `install-task`/`config-concept` keys;
  `audience="admin"`/`product="enterprise"` profiling on the task only)
  matching the examples already in spec §3.2/§4.4, plus a
  `normalized-model.sample.json` that was originally a hand-authored
  stand-in (finding 4) — since corrected to match the real extractor's
  actual output exactly (findings 6–7 found and fixed two spots where
  the original hand-authored version had guessed wrong: the
  `installing-product` → `installing-product-prereqs` link is
  `references`, not `contains`, since it's a bare `href` with no
  `keyref`; and `installing-product-prereqs` itself carries no
  `audience`/`product`, since the source `.dita` file never declared
  any).
- `plugin/org.dita.dita2graph`: `plugin.xml`/`build.xml`/`cfg/*.xml`/
  `bin/dita2graph`/**`lib/dita2graph-core.jar`** per §2.1 — the plugin is
  now **complete and verified end-to-end**, not just installable.
  `plugin/org.dita.dita2graph/java/` is a small standalone Gradle project
  building `ExtractTask` (the `dita2graph:extract` Ant task) and its
  helpers: parses DITA-OT's resolved `.job.xml` plus temp-directory
  topics/maps into the normalized model (§3.2), then shells out to
  `dita2graph-core`. Relation extraction is deliberately limited to what
  DITA markup states directly — map `<topicref>` → `contains`;
  `<xref>`/`<link>` → `requires` if it carries a `keyref`, `references`
  otherwise — leaving `applies-to`/`generated-from` as documented future
  inference work (§3.3, §13), not half-implemented guesses. `related-to`
  is inferred separately, downstream in the Rust core rather than the
  Java extraction layer, from `product` metadata the extractor already
  captures (finding 13). Covered by a real unit test (`DitaModelExtractorTest`, fixture
  shaped like actual DITA-OT 4.4 output) and by the end-to-end run below.
- `gradle-build/`: the real Gradle 9.6.1 project (Kotlin DSL, wrapper
  pinned) used for findings 5–7 — see its own README for how to re-run
  it. `./gradlew buildKnowledgeGraph` now runs the *entire* pipeline for
  real: download DITA-OT, zip and install the plugin, validate, check
  links, run the `dita2graph` transtype, and produce a real
  `okf_validator`-passing bundle. `build/`/`.gradle/` gitignored (an
  ~80MB downloaded DITA-OT install lives there, not something to commit).

8. **Does DITA-OT's validation gate (`DitaOtValidateTask`, §9.3's
   "loud, not silent" claim) actually reject broken source, and does
   *any* kind of broken reference trigger it?** Checked directly with a
   fixture (`sample-docs-invalid/`) rather than assumed — and the answer
   turned out to be more specific than the spec's original phrasing
   ("a deliberately introduced broken `conref`") implied:

   - An unresolvable **`keyref`** (`<xref keyref="does-not-exist"/>`)
     does **not** fail the build. DITA-OT logs `[DOTJ047I] Unable to
     find key definition for key reference 'does-not-exist' in root
     scope. Using the @href attribute as fallback if it exists` — an
     **informational** message (`I` suffix), and the build succeeds
     with the xref's target silently dropped. Tried this first; it was
     the wrong fixture.
   - An unresolvable **`href`** to a file that doesn't exist *does*
     fail, with `[DOTX008E] The resource '...' cannot be loaded ...`
     (an `E`-suffix error) and a non-zero exit code — the fixture
     `sample-docs-invalid/` actually uses.

   This matters beyond just picking the right test fixture: it means
   "broken" isn't uniformly loud in DITA-OT the way §9.3 characterized
   it — a dangling key reference degrades gracefully by design (useful
   for authoring against draft/partial key spaces), while a dangling
   file reference is a hard failure. A future revision of §9.3 should
   say this precisely rather than "broken input fails loudly" as a
   blanket claim.

   **Result:** `gradle-build/build.gradle.kts` gained a
   `validateBrokenDoc` task (deliberately outside `buildKnowledgeGraph`'s
   dependency chain, since it's expected to fail) and
   `.github/workflows/integration.yml` asserts it fails in CI —
   confirmed locally first (`./gradlew validateBrokenDoc; echo $?` →
   `1`), then wired into the same workflow that runs the full
   `buildKnowledgeGraph` pipeline and checks the resulting bundle's
   actual file contents (not just that `dita2graph-core validate`
   exits zero).

9. **Does the public/internal DITAVAL split (§6.1) actually filter
   anything, once a fixture exists to test it against?** Before this,
   `sample-docs/public.ditaval` was an empty `<val>` with a comment
   explaining it had nothing to exclude yet, and `internal.ditaval`'s
   only rule (`<prop att="audience" val="admin" action="include"/>`) was
   a no-op too — `installing-product.dita` has `audience="admin"` on its
   root element, but the *topicref* referencing it in
   `user-guide.ditamap` carries no `audience` attribute, and DITA-OT
   filters branches out of the map based on the topicref's own
   profiling attributes, not (only) the target file's root element. So
   neither DITAVAL file was doing anything, and the "split" was
   aspirational.

   Added `sample-docs/topics/internal-notes.dita` and a topicref for it
   in `user-guide.ditamap` with `audience="internal"` **on the
   topicref**, then re-tested. `public.ditaval` (now
   `<prop att="audience" val="internal" action="exclude"/>`) and
   `internal.ditaval` (adds the matching `include`) were each run
   against a live DITA-OT 4.4, twice: once via the raw `dita` CLI
   (`--filter=sample-docs/public.ditaval` / `internal.ditaval`) and once
   via new `buildKnowledgeGraphPublic`/`buildKnowledgeGraphInternal`
   Gradle tasks (`filter(...)`, confirmed to be the right Kotlin DSL
   call by reading `DitaOtTask`'s source rather than guessing). Both
   ways: the public bundle's `okf/topics/` has no `internal-notes.md`;
   the internal bundle's does; every other file is identical between the
   two. Hit the same recurring `--` (double-dash literal) inside an XML
   comment bug as previous findings while writing `public.ditaval`'s
   updated comment — same fix, watch for it in prose near an em dash.

   **Result:** the split is now backed by a real fixture and a passing
   negative/positive comparison, not just two mostly-empty files. CI
   gates on it (`.github/workflows/integration.yml`: builds both
   profiles, asserts `internal-notes.md` is absent from the public
   bundle and present in the internal one) the same way `validateBrokenDoc`
   gates Phase 4's validation claim.

10. **Does `--args.dita2graph.*=...` actually work from the CLI, the way
    §2.3's invocation example has always shown it?** Checked while
    wiring `args.dita2graph.emit-graph-json` end to end (§12 Phase 1
    status) — and the answer was no, for any of the five parameters,
    not just the new one. `plugin.xml`'s `<transtype
    name="dita2graph">` had no `<param>` children declaring the
    `args.dita2graph.*` family, and DITA-OT 4.4's own CLI parser
    validates `--args.*` values against each transtype's declared
    params before the build even starts: a real run rejected
    `--args.dita2graph.store=none` (an existing parameter, long since

    exactly like the brand-new `--args.dita2graph.emit-graph-json`

11. **Does walking nested `topicref`/`topichead`/`topicgroup` map
    structures (§3.3's long-standing "direct children only" gap) work
    the same way it does for a flat map, once actually tried against a

    running it through a live DITA-OT 4.4 surfaced a second, more

13. **Of the three relation-inference gaps §3.3 has always left open
    (`applies-to`/`related-to`/`generated-from`, findings 6/7 and the
    Phase 1 backlog), which one is actually buildable with data already
    flowing through the pipeline, and which two would require guessing?**
    Checked what `NormalizedTopic` already carries before writing any
    inference code: `product: Vec<String>` (`core/dita2graph-core/src/
    model.rs`) has been extracted by `DitaModelExtractor` since Phase 1
    (`splitAttr(root, "product")`) and flows through to the Rust core
    unused. §3.3's own example — "topics sharing a `product` value are
    `related-to`" — is directly computable from that field alone, no new
    extraction needed. The other two aren't: `applies-to` ("a task's
    `<cmd>` referencing a `<uicontrol>` defined in a reference topic")
    needs `<uicontrol>` element scanning the Java extractor has never
    done, and `generated-from` ("topic → conref/conkeyref source
    fragment") needs `conref`/`conkeyref` provenance tracking that's
    also never been implemented (§3.3's "Deduplication & reuse tracking"
    responsibility, separately still open). Building either without that
    underlying data would mean guessing at a heuristic on partial
    information — exactly what this project's "verify before you infer"
    discipline (§13, findings 6/7) exists to avoid — so both stay
    documented gaps rather than half-implemented guesses.

    Implemented `related-to` inference (`core/dita2graph-core/src/
    relations.rs`, new `infer_related_to`, called from `run_build` in
    `main.rs` before the bundle/graph.json/rag index are written): every
    pair of topics sharing at least one `product` value gets a
    bidirectional `related-to` edge (matching how a real
    `<related-links role="related">` block would appear in both
    topics), unless the pair is already connected by some other relation
    in either direction — an explicit or previously-inferred edge is
    always a stronger signal than "shares a product tag", so it takes
    precedence and the inference is skipped rather than stacked on top.
    The rule is deterministic (share a value or don't), so it never
    needed `DITA2GRAPH010W`'s ambiguity handling — that stays reserved
    for `applies-to`'s genuinely ambiguous case once implemented.

    **Result:** 8 new unit tests (`relations.rs`) cover the shared/
    unshared/no-product cases, the already-connected skip in both
    directions, multiple shared values, and transitive pairwise linking
    across three topics sharing a product. Verified live against a real
    DITA-OT 4.4 run: added `product="enterprise"` to `sample-docs/
    topics/internal-notes.dita` (already `product="enterprise"` on
    `installing-product.dita`, and the two aren't connected by any
    author-declared relation) and rebuilt both the public and internal
    DITAVAL profiles. The internal build's `graph.json` gained exactly
    the two expected edges (`internal-notes --related-to-->
    installing-product` and the reverse), rendered correctly in both
    topics' `# Related` body sections and `okf-validator`-clean; the
    public build — which never sees `internal-notes` at all, per the
    DITAVAL filter (finding 9) — correctly inferred zero `related-to`
    edges, not just omitted the excluded topic's own. Both checks are
    gated in CI (`.github/workflows/integration.yml`).

14. **Of the three map-composition mechanisms the spec has always
    listed as "out of scope, same discipline as `applies-to`/
    `related-to`/`generated-from`" (`<navref>`/`<anchorref>`/
    `<mapref>`), does that blanket claim actually hold once checked
    against real DITA-OT 4.4 behavior, the same way finding 11 checked
    nested map structures instead of assuming they'd need new code?**
    It didn't, for two of the three. Built three small fixtures (not
    checked in as-is; folded into one final fixture below) and ran each
    through a live DITA-OT with `--clean.temp=no` to inspect the actual
    resolved output, rather than reasoning from the DITA spec's prose
    alone:

    - **`<mapref href="submap.ditamap"/>`**: DITA-OT's own preprocessing
      (its `mapref` build step — confirmed present via `dita --help`'s
      `--build-step.mapref=<yes|no>`) flattens the referenced submap's
      `<topicref>` elements directly into the resolved base map before
      this plugin's extractor ever runs. `submap.ditamap` itself still
      appears in `job.xml` as an intermediate file, but never as
      `input="true"`, so `DitaModelExtractor`'s existing map-file
      selection (which only treats the `input` ditamap as *the* map)
      already ignores it correctly, and the existing recursive walk
      (finding 11) already picks up the merged `<topicref>` tree the
      same way it picks up ordinary nesting. **Zero code changes
      needed** — this was already fully supported, and the spec's "out
      of scope" claim for it was simply wrong.
    - **`anchorref`**: the DTD (`map.mod`) clarifies this isn't a
      separate topicref-like element as the spec's prose implied — it's
      an attribute on a submap's *root* `<map>` element
      (`anchorref="some-id"`), paired with an `<anchor id="some-id"/>`
      marker placed somewhere in the base map, intended to splice the
      submap's content at that exact position rather than wherever the
      `<mapref>`/`<topicref>` including it textually sits. Tested with
      the anchor in two different positions (at map level, and nested
      inside a topicref) — both times, DITA-OT merged the submap's
      content in at the *including* topicref/mapref's own location, not
      the anchor's, leaving the `<anchor>` element inert. Since this
      plugin's `contains` edges encode only *which container* a topic
      belongs to, not sibling order, the graph this plugin produces is
      correct either way — so `anchorref` is functionally supported the
      same way `mapref` is, with the one real, verified caveat that its
      documented positional-splicing behavior isn't honored by DITA-OT
      itself (at least not by default, for this transtype).
    - **`<navref mapref="nav.ditamap"/>`**: genuinely unsupported,
      confirmed by the same method — the `<navref>` element survives
      completely unresolved in the resolved base map's output, and the
      referenced map/topics never enter `job.xml` at all. DITA-OT only
      resolves `<navref>` inside output-specific transforms (webhelp/
      eclipsehelp TOC generation), not generically during preprocessing
      the way `mapref` is. Supporting it here would mean this plugin
      parsing and merging referenced navigation maps itself, entirely
      outside DITA-OT's own pipeline — a materially larger, different
      undertaking than the other two, and not attempted. This is the
      one part of the original "out of scope" claim that actually holds.

    **Result:** checked in `sample-docs-mapref/` (`user-guide.ditamap`
    `<mapref>`-including `submap.ditamap`, whose root `<map>` carries
    `anchorref="insert-point"` targeting an `<anchor>` nested inside
    `user-guide.ditamap`'s own `intro` topicref — exercising both
    mechanisms in one fixture, since they behave identically for graph
    purposes) with a `README.md` documenting exactly what was confirmed
    above. `graph.json` for it is exactly `user-guide --contains-->
    {intro, after, spliced}` — `spliced` (from the submap) attaches
    directly to `user-guide`, not nested under `intro` despite the
    anchor's position, matching the caveat above precisely.
    `okf-validator`-clean. Gated in CI
    (`gradle-build/build.gradle.kts`'s `buildKnowledgeGraphMapref`,
    `.github/workflows/integration.yml`) the same way
    `buildKnowledgeGraphNested` gates finding 11. Updated
    `DitaModelExtractor`'s class doc and the spec's §3.3/§12 Phase 1
    status accordingly — `<navref>` is the only one of the three still
    genuinely out of scope.

15. **Of the two remaining relation-inference gaps (`applies-to`,
    `generated-from`, findings 6/7 and 13), what would each actually
    need to become real rather than guessed, and does the DITA-OT
    resolved output already carry the data to build it deterministically?**
    Checked both against real resolved output before writing any
    extraction or inference code, the same discipline as finding 14.

    **`generated-from` needed no inference at all, once the right
    signal was found.** Built a scratch `<p conref="...#.../id"/>`
    fixture and inspected DITA-OT's resolved output directly
    (`--clean.temp=no`): every element it writes carries an `xtrf`
    attribute tracing its *true* source file as an absolute `file:` URI
    — and a `conref`/`conkeyref`-resolved element is replaced wholesale
    by the referenced element, inheriting *its* `xtrf`, not the
    referencing topic's own. Confirmed the negative case mattered too:
    a plain `keyref`-resolved `<keyword keyref="...">`/`<ph>` (ordinary
    variable substitution, not content reuse) keeps its *own* `xtrf`
    unchanged — DITA-OT resolves the `keyref` into an `href` attribute
    and injects text as a child node, but doesn't replace the element
    itself the way conref/conkeyref do. This is the precise
    discriminator §3.3 wants ("topic -> conref/conkeyref source
    fragment", not "topic -> anything referencing a key"), and it's
    deterministic, not a heuristic: `DitaModelExtractor` now builds a
    `src -> path` map from `job.xml`'s own `<file src="...">` entries
    (the same absolute-URI scheme `xtrf` uses, confirmed by comparing
    them directly), scans every descendant element of a topic's body for
    an `xtrf` resolving to a *different* topic than its own, and adds
    one `generated-from` edge per distinct source (deduped per topic,
    not one edge per reused element). Also checked that DITA-OT's
    auto-generated `<related-links>` block (finding 11) doesn't
    contaminate this: its content's `xtrf` points at the *ditamap*, not
    a topic, and it's excluded by the same `isInsideRelatedLinks` check
    the `<xref>`/`<link>` scanner already uses, so it can never resolve
    to a bogus generated-from target anyway.

    **`applies-to` needed real new extraction (`uicontrols`/
    `cmdUicontrols`), then a matching rule precise enough to avoid
    false positives.** `DitaModelExtractor` now collects two per-topic
    fields: `uicontrols` (distinct `<uicontrol>` text anywhere in a
    topic's body -- what a Reference topic "defines") and
    `cmdUicontrols` (distinct `<uicontrol>` text specifically inside
    `<cmd>` elements -- what a Task topic's steps "invoke"), scoping the
    match to §3.3's literal wording rather than any casual mention
    anywhere in a task's prose. `core/dita2graph-core/src/relations.rs`
    gained `infer_applies_to`: for each Task's `cmd_uicontrols` term,
    find every Reference topic whose `uicontrols` contains it. Exactly
    one candidate -> a real edge (once per task/reference pair, even if
    several terms resolve to the same reference). Two or more
    candidates is `DITA2GRAPH010W`'s own canonical example -- the
    catalog entry has said "e.g. two candidate `applies-to` targets"
    since Phase 0, before this was ever built -- so it's dropped and
    logged, not guessed at by picking one. Same "an existing relation in
    either direction wins" precedence as `related-to` (finding 13).
    `applies-to` runs *before* `related-to` in `run_build` (main.rs): a
    directional, type-scoped, unambiguous `<uicontrol>` match is a
    stronger signal than a shared `product` tag, so it gets first claim
    on a pair.

    **Result:** 8 new Rust unit tests (`relations.rs`) cover the
    unambiguous match, the no-match case, the ambiguous-drop (verified
    the diagnostic is actually emitted, not just that no edge appears),
    one task with both an unambiguous and an ambiguous term at once,
    multiple terms deduping to one edge, `cmd`-scoping on the source
    side, Reference-only gating on the target side, and the
    already-connected-elsewhere precedence rule. 2 new Java unit tests
    (`DitaModelExtractorTest`) cover `generated-from`'s per-topic dedup
    (two reused elements from the same source collapse to one edge) and
    `uicontrols`/`cmdUicontrols` extraction scoping. Verified live
    against a real DITA-OT 4.4 run with a purpose-built fixture
    (`sample-docs-relations/`, checked in): a task using `Save`
    (matching exactly one reference topic) and `Cancel` (matching two)
    produces exactly one `applies-to` edge, for `Save` only -- `graph.json`
    has no edge at all involving the second `Cancel`-matching topic, and
    the dropped-match diagnostic shows up in the real `dita` build log.
    A separate `conref`-based reuse in the same fixture produces exactly
    one `generated-from` edge, rendered correctly in both the frontmatter
    link and body of the reusing topic's OKF concept, `okf-validator`-clean.
    Gated in CI (`gradle-build/build.gradle.kts`'s
    `buildKnowledgeGraphRelations`, `.github/workflows/integration.yml`).
    Every relation in §4.3's taxonomy is now real: `contains`,
    `requires`, `references`, `applies-to`, `related-to`, and
    `generated-from`. Canonical-node deduplication for reused content
    and incremental rebuild remain open (§3.3, §12 Phase 2 status).

17. **What did a token/latency benchmark of Claude Code with and without
    the MCP server (`dita2graph-demo/bench`, 8 questions x 3 runs on
    `dita-ot/docs` 4.4.1) show the graph was missing, and can each gap be
    closed from DITA-OT's own resolved output rather than by
    reimplementing DITA semantics?** Four gaps, all closed that way. Each
    mechanism below was confirmed in a kept temp directory of a real
    DITA-OT 4.4.1 run (`--clean.temp=no`), not assumed:

    - **Relationship tables were invisible.** DITA-OT's maplink step
      writes reltable links into each topic's `<related-links>`, the
      block the extractor skipped wholesale to avoid mistaking hierarchy
      navigation for author intent. The two kinds are distinguishable:
      hierarchy links carry `role="parent"`/`"child"`/`"sibling"`/...,
      reltable links carry `role="friend"` (and their `linkpool`'s
      `xtrf` names the map that holds the reltable). Hierarchy roles are
      still skipped; everything else becomes `references` (§4.3 lists
      related-links under it), unless the prose already links the same
      pair.
    - **Reused fragments had no name.** A conref'd element loses its
      `@id` in the reusing topic, but keeps its `xtrc` (element,
      occurrence, line and column in the source file), and the source
      topic's own resolved copy carries that same `xtrc` next to the
      `@id`. `generated-from` now names its fragments
      (`plugins-installing` -> `ID`: `plug-in`, `plugin-integrate-all`),
      falling back to `element@line` from the `xtrc` when there is no id.
    - **Reused text was unreachable.** Canonical-node deduplication
      (rightly) keeps reused blocks out of a topic's own body, and every
      MCP tool returned 140-to-300-character excerpts, so a sentence
      living in a conref warehouse could not be read at all: the Java
      version (`17`, a keyword in a paragraph conkeyref'd from
      `reusable-components.dita`) never reached the agent. The same walk
      now also builds `resolvedBody`, every fragment kept between
      `[reused from <file>#<id>]` and `[end reused]` markers, written to
      the RAG chunk as `resolvedText` and served whole by the new
      `read_topic` tool. Ranking and embeddings keep the deduplicated text.
    - **Resource-only topics sat in the table of contents.** DITA-OT
      cascades `processing-role="resource-only"` onto every topicref it
      covers before this plugin runs, so the topicref's own attribute is
      enough to skip its `contains` edge. The conref warehouses (`ID`,
      reusable components, error-message key target) are no longer
      children of the map, and stay nodes as reuse sources.

    **Result** on `dita-ot/docs`: 536 -> 646 edges; `references` 18 -> 133
    (reltable), `contains` 220 -> 215, the map's direct children 10 -> 7
    (exactly its table of contents), unchanged validation (bundle and RAG
    index OK; the 28 extra unresolved-link warnings all point at
    `parameters/*.dita` and `extension-points/*.dita`, which the corpus's
    own Gradle build generates). Three new Java tests, seven new Rust
    tests (four in the core crate, three in the MCP server).

18. **Why did the graph of a second, larger corpus (the Oxygen XML user
    guide, `oxygenxml/userguide`, a bookmap of 2,757 `.dita` files) miss
    two of its 25 chapters and its whole glossary, and why did one
    `analyze_impact` call sink an agent?** Both surfaced in the
    `dita2graph-demo/bench` Oxygen campaign (questions o4 and o8).

    - **Map elements were matched by name.** DITA-OT renames most bookmap
      `<chapter>`s to `<topicref>` in the resolved map, but leaves two
      kinds as they are (confirmed in a kept temp directory,
      `--clean.temp=no`): a chapter pointing straight at a topic
      (Add-ons) and a navtitle-only chapter (Glossary), whose
      children are `<glossref>`s. `walkMapChildren` switched on
      `topicref`/`topichead`/`topicgroup` and skipped all of them. It now
      recognizes a topicref by `@class` (` map/topicref `), so every
      specialization counts (bookmap `chapter`/`part`/`appendix`/
      `notices`/`frontmatter`/`backmatter`, `glossref`, `keydef`,
      `topichead`, `topicgroup`), and falls back to element names only
      when `@class` is absent (hand-written fixtures). A topicref whose
      `format` is not `dita` (a `ditavalref`, a local PDF) is skipped
      through, like an external one.
    - **Headings had nowhere to live.** An href-less entry with a
      navtitle (`<topichead>`, the navtitle-only Glossary chapter) is what
      a reader sees in the table of contents. It now becomes a node of
      type `Topic Head` (id `topichead--<slug>`), contained by its parent
      and containing its children, and consumes a depth level. Its
      `resource` is `<map>#<id>`: the OKF validator treats `resource` as
      a concept's identity, and the bare map path already belongs to the
      map node (the first rebuild failed on exactly that). `validate_live`
      strips the fragment. A `<topicgroup>` (DITA-OT wraps resolved
      submaps in one) or an untitled href-less topicref stays transparent.
      A bookmap's title is read from `booktitle/mainbooktitle`.
    - **One impact analysis was too large to read.** On the reused phrase
      of question o8 (`reusables-preferences-pages`), `analyze_impact`
      returned 613 lines; Claude Code saved the result to a file the
      MCP-only agent could not open, and it fell back on up to 160 small
      calls. The tool now leads with totals (by relation and by level),
      pages its entries (`limit`, default 40, `0` for counts only;
      `offset`), can drop the excerpts, and takes a `fragment` to keep
      only the topics reusing one element of the source topic.

    **Result** on the Oxygen guide (`editor-sa.ditaval`): 2,041 -> 2,045
    nodes (four `Topic Head`s: Glossary and three WebHelp search
    headings), 9,922 -> 9,968 edges; the map now contains its 25
    chapters plus the copyright notice, and Glossary contains its 40
    entries. `analyze_impact` on `reusables-preferences-pages` with
    `limit=0` answers in one 204-character line (1,637 concepts within
    depth 5); with `relation=generated-from`, `fragment=
    open-the-preferences-page` and `depth=1` it counts 217 topics, the
    number DITA-OT itself resolves (215 published pages plus two conref
    warehouses outside the table of contents), without mixing in the
    sibling phrase `Open-the-preferences-page`. Rerun on Opus, the
    MCP-only configuration went from 93 % to 100 % quality and from 3.7x
    to 5.1x fewer tokens than reading the raw sources; on o8 alone, from
    158 to 17 tool calls. Bundle and RAG index validate. The
    `dita-ot/docs` graph is unchanged (its map has no titled heading).
    One new Java test (bookmap), two updated (the nested fixture's
    `topichead` is now a node), one new Rust test in the core crate, two
    in the MCP server; CI's nested-map assertion updated to match.

    Still open, found by the same rerun: a topic referenced with
    `chunk="to-content"` (`simple-dita-ot-plugin`) keeps neither title
    nor text in the graph, since DITA-OT moves its content into the topic
    that absorbs it.

19. **Why did 154 topics of the Oxygen XML user guide have no parent in
    the table of contents, and why did 133 others have two?** Found while
    reviewing the RDF/SHACL specification: a SHACL shape "a published
    topic has a parent" would have flagged 235 topics on the current
    graph. Most were `copy-to` copies. Confirmed in a kept temp directory
    of a DITA-OT 4.4.1 run on a three-topic `copy-to` fixture:

    - **The resolved topicref keeps `href` on the source.** DITA-OT
      writes `<topicref href="topics/shared.dita"
      copy-to="topics/shared-2.dita">` and the copy as its own job.xml
      file. The extractor followed `href`: the source got both TOC
      entries, the copy none.
    - **The copy shares its source's `src` in job.xml.** The `src` →
      path table used for `xtrf` traces kept whichever file came last, so
      a source and its copy looked like one reused the other's whole
      content, in a direction that depended on job.xml's order.
    - **The copy could take the clean id.** Duplicate ids went to the
      first file read; on the Oxygen guide the copy came first, so
      `create-new-project` named `create-new-project-2.dita` and the
      real topic became `create-new-project--topics-create-new-project.dita`.

    **Fix** in `DitaModelExtractor`: a topicref with a `copy-to` whose
    file is in job.xml contains the copy; sources are parsed before their
    copies, so the source keeps its id and the copy gets the suffixed one
    (`DITA2GRAPH071I`, info, instead of `DITA2GRAPH070W`); the `src` →
    path tables prefer the source, so every copy now has one
    `generated-from` edge to its source. One new Java test.

    **Result** on the Oxygen guide: 158 copies recognized, 0
    `DITA2GRAPH070W` (all the duplicates were copies), topics without a
    parent 235 → 81 (34 reuse warehouses, 46 `chunk="to-content"` topics,
    one real duplicate id), topics with two parents 133 → 0; same node
    and edge counts (2,045 and 9,968). `dita-ot/docs` has no `copy-to`
    and is unchanged.

20. **What does a DITA-OT 4.4.1 resolved temp directory still say about
    keys, external links and `coderef`, and what did `requires` really
    mean?** Checked in a kept temp directory of the `dita-ot/docs` build
    (`--clean.temp=no`), for phase 4 of the semantic model
    (`docs/semantic-model.md`):

    - **Key definitions survive.** Every `<keydef>` and topicref with
      `@keys` of every submap is in the resolved root map (606 `@keys`),
      with its resolved `href`, `scope`, `format` and the `xtrf` of the
      submap that wrote it; DITAVAL has already removed the filtered ones.
    - **`@keyref` survives, `@conkeyref` does not.** 550 `@keyref` remain
      on resolved topics (405 on `xref`, 129 on `keyword`, 14 on `link`),
      the external ones with the resolved URL in `href`. No `@conkeyref`
      is left: DITA-OT turns it into a conref, then resolves it away.
    - **`coderef` is gone.** No `<coderef>` element remains; the file's
      text is inside the `codeblock`, whose `xtrc` still names it, and
      job.xml lists the 40 included files (`format="coderef"`) without
      saying who includes them.
    - **`requires` did not mean prerequisite.** It was any link made
      through a key: 127 edges on `dita-ot/docs`, 1,559 on the Oxygen
      guide. The task `<prereq>` sections of `dita-ot/docs` link only to
      external sites, and the Oxygen guide has one local prerequisite
      link.

    **Fix** in `DitaModelExtractor`: the map's key definitions become the
    map node's `keyDefs` (first definition per scope wins, the defining
    submap from `xtrf`); each topic gets `keyrefs`, `externalLinks`
    (absolute `http(s)` URLs) and `codeRefs`. `coderef` and `@conkeyref`
    are read from the topic's source file (job.xml `src`) and kept only
    when the resolved topic confirms them: the `coderef`'s parent element
    is still there (same `xtrf` and element counter), the conkeyref's key
    names a topic this one reuses (`generated-from`). A source that does
    not parse on its own is skipped with `DITA2GRAPH072I`. `requires` is
    now a task's `<prereq>` link or a task's link with
    `importance="required"`; every other link is a `references`, one edge
    per pair. Topic types come from `@class` (`troubleshooting` added,
    specializations take their base type), and a `copy-to` copy gets a
    `copy-of` link to its source. The core writes the declarations into
    the OKF concepts, as key, URL and file nodes of `graph.json` and
    `graph.db`, and into the RDF export; the MCP tools traverse them.
    Three new Java tests.

    **Result:** `dita-ot/docs` gets 608 keys, 431 external URLs (507
    `links-to`), 510 `uses-key` and 40 sample files (46 `includes-code`),
    and 0 `requires`; the Oxygen guide 243 keys, 1,008 URLs, 5,163
    `uses-key`, 158 `copy-of`, 68 troubleshooting topics and 1 `requires`.
    No topic of either corpus uses an undefined key, no source failed to
    parse, and both RDF exports validate without a violation (47 warnings
    on the Oxygen guide, down from 50: the 3 `copy-to` sources now
    count as published through their copies).

    Rebuilding the benchmark bundles also showed that a copy's two links
    to its source (`# Generated From` and `# Copy Of`) added 158
    okf_validator "redundant link" warnings to the 274 the Oxygen guide
    already had (a child also referenced, a reuse source also linked).
    `render_concept` now links each target once per concept and names it
    under later headings: 0 warnings on both corpora, down from 107 and
    435. The same rebuild skipped every concept file, since only the
    rendering had changed: the incremental fingerprint now includes a
    `RENDER_VERSION`, bumped with any change to the concept layout.

    **Benchmark** (`dita2graph-demo/bench`, campaign 4 replayed: 12 real
    questions, 3 configurations, 3 repetitions, Opus, graded blind with
    the original answers mixed in): with the MCP server alone, writers'
    questions 63 → 86 % and users' 83 → 96 % (sans MCP 97 → 97 %). The
    link and key questions moved most: EULA links 33 → 90, the HTML Help
    Workshop link 60 → 100, the license transfer impact 50 → 83, renaming
    an id 25 → 100. On the Oxygen guide, the MCP-only session spends 41 %
    fewer tokens (875k → 515k) and 38 % less time, now below sans MCP on
    both corpora. Still missing for the 90 % exit criterion: composite
    `.dita` files (a root `<reference>` holding nested topics, such as
    `release-notes/index.dita` and `parameters/ant-parameters-details.dita`)
    give empty text, since only the root's body is read (r-d6: 67); the
    MCP tools do not say a topic is resource-only, so a reuse warehouse
    is counted as a published page (r-o8: 90); and r-o9 needs a map the
    Editor DITAVAL removes, outside the published graph by design.

    **Fixed after the benchmark.** The title, summary and body of every
    nested topic now join the text of their file's topic: on
    `dita-ot/docs`, no topic is left without text (5 before), and the
    release notes (17,500 characters) and Ant parameter details now
    contain `outputFile.base`; on the Oxygen guide, 160 remain (207
    before): 156 `copy-to` copies, whose text is their source's, and 4
    outline headings. That text quoted markdown examples
    (`[a link](topic.md)` in `Markdown-DITA-syntax`), which okf_validator
    took for 8 dangling links and which failed the build:
    `render_concept` now escapes `](` in the topic text (`RENDER_VERSION`
    3). `graph.json` and `graph.db` carry each topic's `processingRole`,
    and every MCP tool marks a resource-only topic with
    `[resource-only: not a published page]` (10 such topics on
    `dita-ot/docs`, 31 on the Oxygen guide).

    **Code review of phases 4 and 5** (15 findings, all fixed): keyrefs
    resolve in the key scopes of the topicrefs naming the topic (parent
    scope first, as DITA-OT's `KeyrefReader` does); key definitions come
    from every topicref of the map, relationship tables and topicrefs
    beyond `args.dita2graph.depth` included; a glossentry's text is its
    `glossdef` and its `glossBody` again (the `@class` body lookup had
    picked `glossBody` alone); `analyze_impact` reaches a glossary key's
    users through the key and counts only concepts in its totals; a huge
    `limit` or `offset` no longer overflows (it took the server down);
    nothing points at a skipped draft; a class-less `keydef` is
    resource-only; a topic named like the map gets a suffixed id;
    `graph_view` keeps the last of two nodes sharing an id, as `okf/`
    does, and the map's keys before the topics using them; link syntax is
    escaped in titles and key text too (`RENDER_VERSION` 4); `d2g:copyOf`
    is a `prov:wasDerivedFrom`, not a `d2g:generatedFrom`; the node/edge
    view is built once per build; a topic's source is read only when it
    can hold a `coderef` or a `conkeyref`; prefixes and export file names
    have one definition; a declared node is known by its type.

    **Phase 5 campaign** (`dita2graph-demo/bench`, 72 runs: the 12 real

    **Relationship-table keys and copied descriptions.** Writing a README
    query for "pages that write out a URL a key already names" gave 78
    results on `dita-ot/docs`, almost all wrong. Two causes, both in the
    resolved related links. A link DITA-OT's maplink step generates from a

    `<topicref keyref="ant-manual">` becomes a plain

    used by the topic showing the link. Second, DITA-OT copies the target's
    title and shortdesc into each generated link, with the target's own
    `xref` and `keyref`; the extractor counted them as the linking topic's.
    It now skips everything inside a `<link>`. On `dita-ot/docs`: 51

    pages on `dita-ot/docs` (two Markdown topics writing the URL out, and
    `migrating-to-3.7`) and 6 on the Oxygen guide, each checked in the
